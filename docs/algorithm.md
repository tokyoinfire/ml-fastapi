# Алгоритм прогнозирования churn

Описание ML-части сервиса: как данные превращаются в модель и как модель выдаёт предсказание.
Код: `app/ml/preprocessing.py`, `app/ml/training.py`, `app/ml/model_store.py`.

## Задача

Бинарная классификация: по признакам клиента предсказать, уйдёт ли он (`churn = 1`) или останется (`churn = 0`).
Кроме класса модель возвращает вероятность ухода — её удобнее использовать для ранжирования клиентов
по риску, чем жёсткий порог.

## Данные

`data/churn_dataset.csv` — 2000 клиентов, 9 признаков и целевая метка.

Классы несбалансированы: 1597 клиентов остались (≈ 80%) и 403 ушли (≈ 20%).
Поэтому accuracy сама по себе мало что говорит: модель, которая всегда отвечает «не уйдёт»,
получила бы ≈ 0.80.

| Признак | Вид | Обработка |
|---|---|---|
| `monthly_fee`, `usage_hours` | числовой (float) | StandardScaler |
| `support_requests`, `account_age_months`, `failed_payments` | числовой (int) | StandardScaler |
| `autopay_enabled` | бинарный флаг 0/1 | StandardScaler (как числовой) |
| `region`, `device_type`, `payment_method` | категориальный | OneHotEncoder |

Списки признаков заданы явно в `preprocessing.py` (`NUMERIC_FEATURES`, `CATEGORICAL_FEATURES`),
а их порядок (`FEATURES`) одинаков при обучении и предсказании.

## Подготовка данных (`prepare_data`)

1. Проверка датасета: загружен, не пуст, есть все нужные колонки.
2. Строки без метки `churn` отбрасываются.
3. Проверка, что в данных есть оба класса — иначе обучать классификатор бессмысленно.
4. Пропуски в числовых признаках заполняются медианой, в категориальных — значением `unknown`.
5. Результат — матрица признаков `X` (колонки строго в порядке `FEATURES`) и вектор `y`.

## Разбиение (`split_data`)

`train_test_split` с `test_size=0.2`, `random_state=42` и `stratify=y`: 1600 объектов в train и 400 в test.
Стратификация сохраняет долю ушедших в обеих частях (322 / 1278 в train, 81 / 319 в test),
поэтому метрики на test сопоставимы между запусками. Фиксированный `random_state` делает разбиение
воспроизводимым: разные модели сравниваются на одной и той же тестовой выборке.

## Pipeline

Предобработка и модель собраны в один `sklearn.pipeline.Pipeline`:

```
Pipeline
├── preprocess: ColumnTransformer
│   ├── num: StandardScaler     → числовые признаки
│   └── cat: OneHotEncoder(handle_unknown="ignore") → категориальные признаки
└── model: LogisticRegression | RandomForestClassifier
```

Зачем один объект:
- параметры масштабирования и словарь категорий вычисляются только на train, без утечки из test;
- на предсказании применяется ровно та же предобработка, что и при обучении;
- сохраняется и загружается одним файлом.

`handle_unknown="ignore"`: если на предсказании придёт незнакомая категория (например, новый регион),
она кодируется нулевым вектором, а не вызывает ошибку.

## Модели

Тип модели выбирается полем `model_type` в `POST /model/train`, гиперпараметры из `hyperparameters`
дополняют значения по умолчанию из `MODEL_REGISTRY`:

| `model_type` | Модель | Параметры по умолчанию |
|---|---|---|
| `logreg` | `LogisticRegression` | `max_iter=1000`, `class_weight="balanced"` |
| `random_forest` | `RandomForestClassifier` | `n_estimators=200`, `class_weight="balanced"`, `random_state=42` |

`class_weight="balanced"` увеличивает вес редкого класса (ушедших) обратно пропорционально его доле.
Без этого модели склонны почти всегда предсказывать «не уйдёт» и пропускать большинство ушедших клиентов.

- **Логистическая регрессия** — линейная модель: быстрая, устойчивая, хорошо калибрует вероятности
  и требует масштабирования признаков (поэтому в pipeline есть StandardScaler).
- **Случайный лес** — ансамбль деревьев: ловит нелинейности и взаимодействия признаков,
  масштабирование ему не нужно, но не мешает.

## Метрики

Считаются на тестовой выборке после обучения и сохраняются в истории (`GET /model/metrics`):

| Метрика | Что показывает |
|---|---|
| `accuracy` | доля верных ответов; при дисбалансе классов завышает качество |
| `f1` | баланс точности и полноты по классу «ушёл» — главная метрика для поиска уходящих клиентов |
| `roc_auc` | насколько хорошо модель ранжирует клиентов по риску; считается по вероятностям `predict_proba`, не зависит от порога. 0.5 — случайное угадывание, 1.0 — идеальное разделение |

## Результаты

Тестовая выборка 400 объектов, порог классификации 0.5:

| Модель | Параметры | accuracy | f1 | roc_auc |
|---|---|---|---|---|
| logreg | по умолчанию | 0.590 | 0.354 | 0.611 |
| logreg | `C=0.1` | 0.588 | 0.348 | 0.612 |
| random_forest | `n_estimators=200` | 0.690 | 0.244 | 0.583 |
| random_forest | `n_estimators=300, max_depth=8` | 0.637 | 0.293 | 0.601 |

Выводы:
- По `roc_auc` и `f1` логистическая регрессия немного лучше леса, поэтому она — модель по умолчанию.
- Более высокая accuracy леса объясняется тем, что он чаще предсказывает класс большинства
  («не уйдёт»): правильных ответов больше, но ушедших клиентов он находит хуже (ниже f1).
- `roc_auc ≈ 0.6` у всех моделей — сигнал в признаках слабый. Подбор гиперпараметров почти ничего
  не меняет: улучшения стоит искать в данных и признаках, а не в настройке моделей.

## Сохранение и загрузка

После обучения `save_churn_model` сохраняет через `joblib` словарь (bundle) в `models/churn_model.joblib`:

| Ключ | Содержимое |
|---|---|
| `pipeline` | обученный Pipeline (предобработка + модель) |
| `trained_at` | время обучения (UTC) |
| `metrics` | метрики на тестовой выборке |
| `model_type`, `hyperparameters` | тип модели и итоговые параметры после слияния с дефолтами |
| `features` | список признаков, на которых обучена модель |

При старте сервиса модель загружается автоматически. Если сохранённый `features` не совпадает
с текущим `FEATURES` (поменялся набор признаков), модель считается устаревшей и не загружается —
нужно переобучить её через `POST /model/train`.

## Предсказание (`predict_churn`)

1. Объекты `FeatureVectorChurn` превращаются в DataFrame с колонками строго в порядке `FEATURES`.
2. Pipeline применяет ту же предобработку, что и при обучении, и вызывает `predict` и `predict_proba`.
3. Для каждого клиента возвращаются класс `churn`, вероятность ухода `churn_probability`
   и вероятности обоих классов.

Класс определяется по порогу 0.5. Если важнее не пропустить уходящих клиентов, можно ориентироваться
на `churn_probability` с более низким порогом.

## Ограничения и что можно улучшить

- Метрики оцениваются на одном разбиении train/test; кросс-валидация дала бы более надёжную оценку
  и разброс метрик.
- Порог 0.5 фиксирован; его можно подбирать под нужный баланс точности и полноты.
- Новые признаки (динамика использования, история платежей) скорее всего дадут больше,
  чем подбор гиперпараметров.
- Можно попробовать градиентный бустинг — для этого достаточно добавить модель в `MODEL_REGISTRY`
  и её имя в `ModelType`.
